# Нагрузка: где упирается Pulse

Задача 6 из `docs/PLAN-2.md`. Прогоны 1 ноября 2026 в облачной сессии; как повторить — в
[README.md](README.md).

## Вкратце

- **300 посетителей одновременно стек держит спокойно**: ни одной ошибки, ответы API за 8 мс (p95),
  снимок рынка по стриму через 18 мс, бэкенд — меньше половины ядра и 540 МБ памяти.
- **Первым упирается лимит `pulse.limits.stream-clients: 300`.** На 301-м открытом стриме сервер
  отказывает. При всплеске «500 заходов за минуту, 45 секунд на странице» одновременно открыто
  около 375 стримов, и 15% посетителей остались без живых данных.
- **Вторым — трафик стрима**: ~39 КБ/с на зрителя со сжатием, которое включают браузеры
  (140 КБ/с без него). 300 зрителей — ~94 Мбит/с исходящего. Домашнему каналу мака это не под
  силу задолго до 300; серверу Oracle (1 Гбит/с на ядро, 10 ТБ в месяц бесплатно) — легко.
- **Третьим — память бэкенда**: при перегрузке она дошла до 1.38 ГБ при лимите контейнера 1.5 ГБ.
- Процессор, база и Caddy узким местом не были.
- Найдена и исправлена ошибка браузера: отказанный клиент переподключался каждые полсекунды.

## Как мерили

- Стенд: `compose.prod.yaml` (PostgreSQL, бэкенд, Caddy) с `loadtest/compose.loadtest.yaml`:
  вместо бирж выдуманный рынок `FakeExchange` — 530 пар, стаканы 60 из них, тикеры и цены
  маркировки раз в секунду, свеча каждой пары раз в секунду, 3 ликвидации в секунду, диффы
  стаканов 4 раза в секунду. Binance из облака недоступен (451), поэтому так.
- Машина: облачный контейнер, 4 vCPU, 15 ГБ. k6 работал на той же машине и сам съедал до ядра,
  так что запас по CPU у сервера на деле больше. Образы собраны из jar и сборки сайта снаружи
  Docker (`--local-build`: внутри сборки Gradle не проходил прокси), на тех же базовых образах и
  с теми же флагами JVM (`MaxRAMPercentage=70`, `mem_limit: 1536m`).
- Загрузка контейнеров — `docker stats` каждые 5 секунд; «ядро» ниже — 100% одного ядра.
- Сжатие: k6 не умеет `permessage-deflate`, поэтому его трафик — без сжатия. Сколько даёт
  сжатие, померено отдельно: клиент на Python договорился с сервером о `PerMessageDeflate`, а те же
  30 секунд сообщений сжаты так, как это делает расширение (общий словарь, sync flush).

### Важная оговорка про фейковый рынок

В нём **каждая** из 530 пар меняет цену каждую секунду. На настоящем рынке за секунду меняется
меньше пар, так что поток к зрителю в реальности меньше. Цифры трафика ниже — верхняя оценка.

## Результаты

### 1. 300 посетителей (`visitors.js`, `VUS=300`)

Разгон за минуту до 300, 3 минуты удержания; каждый посетитель держит страницу 60 секунд.
1149 визитов (70% лендинг, 30% терминал), 13 тыс. запросов.

| Что | Значение |
|---|---|
| Ошибки HTTP | 0 из 12 990 |
| Отказы стрима | 0 из 1 149 |
| Ответ 429 (лимит запросов) | 0 |
| Время ответа API, p95 / p99 | 8 / 21 мс |
| `/api/candles` (1000 свечей), p95 | 9 мс |
| Снимок рынка после подключения, p95 | 18 мс |
| Бэкенд CPU, среднее / пик | 0.43 / 0.79 ядра |
| Бэкенд память, пик | 539 МБ |
| Caddy CPU, среднее / пик; память | 0.19 / 0.44 ядра; 157 МБ |
| PostgreSQL | 0.02 ядра, 77 МБ |
| Трафик стрима (без сжатия) | 37 МБ/с, ~123 КБ/с на зрителя |

### 2. 600 посетителей (`VUS=600`, удержание 2 минуты)

Стримов больше 300 не открылось: 97% попыток подключиться к стриму получили отказ — это лимит
`stream-clients`. Отказанные виртуальные посетители тут же заходили снова, без паузы, и устроили
28 тыс. попыток подключения и 286 тыс. запросов к API за 4 минуты. Под этим штормом:

| Что | Значение |
|---|---|
| Ошибки HTTP | 1 из 286 256 |
| Время ответа API, p95 / p99 | 461 / 685 мс |
| `/api/candles`, p95 | 596 мс |
| Снимок рынка, p95 | 817 мс |
| Бэкенд CPU, среднее / пик | 0.86 / 1.61 ядра |
| **Бэкенд память, пик** | **1 383 МБ из 1 536** |
| Caddy CPU, среднее / пик | 0.94 / 1.64 ядра |

Сервер не упал и отвечал, но в памяти почти не осталось запаса: ещё немного — и JVM вышла бы по
`ExitOnOutOfMemoryError` (контейнер перезапустится, но все зрители отвалятся разом).

Шторм повторных заходов — не только артефакт теста. Браузер вёл себя так же: сервер при
перегрузке сначала принимает сокет, а потом закрывает его с кодом 1013, и клиент
(`web/src/market.ts`) сбрасывал паузу переподключения на `onopen`, то есть стучался снова через
0.5 секунды, бесконечно. **Исправлено в этой ветке**: пауза сбрасывается только когда пришли данные,
а на 1013 клиент ждёт 5–10 секунд (со случайным разбросом, чтобы не прийти всем разом).
Проверка — `web/e2e/stream.e2e.ts`: со старым кодом 4 попытки за 4 секунды, с новым не больше 2.

### 3. Всплеск: 500 заходов за минуту (`burst.js`)

Каждый посетитель держит лендинг (или терминал, каждый пятый) 45 секунд, так что в пике открыто
около 375 стримов.

| Что | Значение |
|---|---|
| Ошибки HTTP | 0 из 4 900 |
| **Отказы стрима** | **76 из 500 (15%)** |
| Время ответа API, p95 | 5 мс |
| Снимок рынка, p95 | 16 мс |
| Бэкенд CPU, среднее / пик | 0.44 / 0.71 ядра |

Отказанные 15% видят страницу, но без живых чисел (терминал пишет «переподключение») — для
человека из TikTok, который пришёл посмотреть «как это работает», это провал первого впечатления.

### 4. Сжатие стрима

| | Без сжатия | С `permessage-deflate` |
|---|---|---|
| Снимок рынка при подключении | 169 КБ | 44 КБ |
| Поток | 140 КБ/с | 39 КБ/с (×3.6) |

Сервер (Tomcat в Spring Boot) договаривается о сжатии сам, браузеры его просят — то есть
настоящий зритель стоит ~39 КБ/с. Цена — процессор бэкенда на сжатие каждому клиенту отдельно;
в прогонах k6 её нет, так что CPU с настоящими браузерами будет выше, чем в таблицах.

## Что во что упирается

1. **Лимит стримов 300** — срабатывает первым, и это настройка, а не железо: при 300 клиентах
   бэкенд был загружен меньше чем наполовину.
2. **Исходящий канал.** 39 КБ/с × зрители: 100 зрителей ≈ 31 Мбит/с, 300 ≈ 94 Мбит/с. Пока стек
   живёт на маке за туннелем Cloudflare, потолок — домашняя отдача (обычно 20–50 Мбит/с, то есть
   ~60–150 зрителей одновременно), и он наступит раньше лимита. На Oracle A1 канал не ограничение,
   а бесплатные 10 ТБ в месяц — это ~70 тыс. часов просмотра (39 КБ/с ≈ 140 МБ в час на зрителя).
3. **Память бэкенда.** 1.5 ГБ на контейнер мало для лимита выше 300: на 300 рабочих клиентах 540 МБ,
   но под штормом подключений — 1.38 ГБ.
4. **Лимиты на адрес** (`stream-clients-per-address: 8`, `requests-per-minute: 120`). В тесте
   у каждого посетителя свой адрес, и 429 не было ни одного. Но мобильные операторы сажают тысячи
   абонентов за один адрес (CGNAT): зрители TikTok с одного оператора могут упереться в 8 стримов
   на адрес раньше, чем в общий лимит. В облаке это не проверить — смотреть в логах на сервере.
   IPv6 считается по сети /64, а не по адресу: у телефона в мобильной сети своя /64, и любой
   адрес в ней — тот же абонент; иначе скрипт обходил бы лимиты, меняя адрес на каждый запрос.
5. Процессор, база и Caddy — с большим запасом.

## Рекомендации

По порядку пользы:

1. **Переезд на сервер до запуска ролика** (задача 5, `deploy/oracle/`): с мака за туннелем
   одновременно поместится 60–150 зрителей, и сделать с этим ничего нельзя.
2. **На сервере поднять лимиты вместе с памятью**: `mem_limit` бэкенда 3 ГБ и
   `stream-clients: 800` (на A1 с 12 ГБ памяти хватает). Перед запуском повторить
   `loadtest/run.sh burst -e ARRIVALS=1000` на самом сервере или такой же машине: отказов должно
   быть 0, память — с запасом от лимита.
3. **`stream-clients-per-address` поднять до 30–50** — ради CGNAT мобильных операторов.
   Защиту от одного назойливого скрипта даёт и общий лимит, и лимит запросов.
4. **Лёгкий стрим для лендинга.** 70% посетителей — лендинг, которому для планеты, бегущей строки
   и четырёх чисел не нужны все поля всех 530 пар дважды в секунду. Отдельный поток раз в 2–5
   секунд с ценой, изменением за 24 часа и объёмом (или `/api/summary` с кэшем) снизит трафик и
   число тяжёлых клиентов в разы. Это самая большая экономия, но это изменение кода — решение за
   владельцем.
5. **Закрывать стрим скрытой вкладки** (через минуту после `visibilitychange` → `hidden`) и
   открывать снова при возвращении: вкладки, забытые после ролика, не будут занимать места.
6. Исправление переподключения из этой ветки — смержить вместе с остальным.

Не финансовый совет.
