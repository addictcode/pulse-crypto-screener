# Нагрузочный тест

Сценарии на [k6](https://k6.io) (запускается из образа `grafana/k6`, ставить ничего не нужно)
против прод-стека из `compose.prod.yaml`. Вместо Binance и Bybit бэкенд кормит выдуманный рынок
(`pulse.fake-market.enabled`, `dev.pulse.exchange.fake.FakeExchange`): 530 пар, 60 стаканов,
частота обновлений как у биржи. Так тест не зависит от сети и одинаков на любой машине. Цифры
фейковые, на сайте этот режим не включается.

Результаты прогонов и выводы — в [REPORT.md](REPORT.md).

## Сценарии

- `visitors.js` — N посетителей одновременно (`-e VUS=300`): 70% на лендинге, 30% в терминале.
  Каждый открывает страницу со скриптами и стилями, делает те же запросы к API, что и браузер
  (терминал: свечи, позиционирование, сравнение с Bybit, сигналы, статистика, сетапы, ссылки),
  и `STAY` секунд (60) получает данные, как браузер: терминал держит стрим `/ws/market`, лендинг
  раз в 5 секунд спрашивает `/api/summary` (с ноября 2026; отчёт `REPORT.md` снят до этого, когда
  лендинг тоже держал стрим). Потом приходит следующий. Разгон
  минута, удержание `HOLD` (3m).
- `burst.js` — всплеск после ролика: `ARRIVALS` (500) заходов, равномерно за минуту, каждый
  смотрит 45 с; каждый пятый идёт в терминал.

Каждый виртуальный посетитель — свой адрес (`X-Forwarded-For`, Caddy верит ему только от соседа
по Docker-сети), иначе лимиты `pulse.limits` на адрес резали бы тест, а не сервер.

Свои метрики: `stream_bytes` (сколько пришло по стриму), `summary_bytes` (сколько лендинг получил
сводками, сжатыми, — только ответы с `Content-Length`; весь трафик — встроенная `data_received`), `stream_first_message_ms` (через
сколько после подключения пришёл снимок рынка), `stream_refused` (сервер закрыл стрим без данных —
лимит клиентов), `api_rate_limited` (ответы 429).

## Запуск на маке

Нужен запущенный Docker Desktop. Из корня репозитория:

```bash
loadtest/run.sh visitors -e VUS=300
```

```bash
loadtest/run.sh burst
```

```bash
loadtest/run.sh up      # только поднять стек и дождаться здоровья, без k6 (для обхода web/e2e-stack)
loadtest/run.sh down
```

Первый запуск собирает образы (5–10 минут). Стенд — отдельный проект `pulse-load` на
`http://localhost:8088`, живой стек на маке он не трогает (своя база, свои порты). Каждый прогон
пишет в `loadtest/results/<сценарий>-<время>/`: вывод k6 (`k6.txt`, `summary.json`), загрузку
контейнеров каждые 5 секунд (`stats.csv`: CPU в процентах одного ядра, память, сеть) и лог бэкенда.
`down` останавливает стенд и удаляет его базу.

Если сборка образа падает на скачивании зависимостей (так было в облаке за прокси), первый
аргумент `--local-build` собирает jar и сайт снаружи Docker и упаковывает их в те же базовые
образы; следующие запуски используют собранное (`loadtest/.build/`).

Лучше гонять тест на другой машине, чем стек: k6 на 300 посетителях сам ест около ядра.
Против уже работающего стека (например, на сервере) — без `run.sh`:

```bash
docker run --rm -i -v "$PWD/loadtest:/t" grafana/k6:0.57.0 run -e BASE=https://mypulse.duckdns.org -e ORIGIN=https://mypulse.duckdns.org -e VUS=100 /t/visitors.js
```

С настоящего сервера все виртуальные посетители придут с одного адреса, и лимиты на адрес
сработают раньше всего остального — для замера сервера это не годится, только для проверки
лимитов.
