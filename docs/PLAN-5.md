для облачных сессий. Оценка — около 100 часов в восьми фазах. Фазы идут по порядку; внутри фазы

## Откуда этот план

**PLAN-4.** Блоки A (игра, пуши, онбординг, бот) и F (SEO, лендинг, «поделиться», языки) сделаны и
вмержены 8–9 ноября (PR #30–#37). Блоки B, C, D, E, G не начаты: они вошли сюда, в новом порядке,
и PLAN-4 по ним больше не ведётся.

**Полная проверка 9 ноября.** После мержа всех восьми PR прогнано всё. Тесты зелёные: бэкенд с
Testcontainers, 152 юнит-теста сайта, 104 e2e, ролики, `tsc`, `npm audit`. Потом прод-стек
(`compose.prod.yaml` + `FakeExchange` + Caddy) обошёл настоящий браузер: каждая страница, десктоп и
телефон, EN и RU. Нашлось четыре ошибки, которых тесты не видели (исправлены в PR «Исправления
после полной проверки»):

1. **Лендинг, `/record/` и игра ездили вбок на телефоне.** Четыре кнопки языка из F4 и «Открыть
   терминал» не помещались в шапку, кнопка терминала обрезалась. Теперь на узком экране
   переключатель свёрнут до текущего языка.
2. Заголовок «СТАТИСТИКА» на `/record/` был шире экрана 360 px.
3. **Тур по терминалу на телефоне** показывал на список рынка, уехавший за экран, когда приходили
   строки, а последний шаг советовал Ctrl K.
4. Без ключей VAPID каждый заход в терминал писал в консоль 404 от `/api/push/key`.

**Вывод.** e2e идут на поддельном бэкенде и проверяют поведение, а не вёрстку и не настоящий стек.
Поэтому первая фаза — сеть безопасности, которая ловит такие ошибки сама, до владельца.

## Правила для исполнителя

Действуют правила из `CLAUDE.md`. Главное:

- **Ветка и PR на задачу**, в `main` не пушить и не мержить: мержит владелец. Если задача зависит
  от незамерженной ветки, начинать от неё и писать это в PR.
- Коммиты и PR по-русски. **Никаких `Co-Authored-By`, «Generated with/by Claude Code» и ссылок на
  сессию** ни в коммитах, ни в описаниях PR: облако дописывает их само, проверять и убирать.
- Перед коммитом — сборка и тесты задетого, CI зелёный. Строки интерфейса — с переводом в
  `locale-ru.ts` (и в `locale-es.ts` / `locale-tr.ts`, если строка на публичной странице: тест
  ловит пропуск). Изменил расчёты на Java — поправь `web/src/lite/` (сверяет `parity.json`).
- **Новая вёрстка проверяется на телефоне 320, 360 и 390 px**, на всех языках страницы
  (`e2e/phone-layout.e2e.ts`, с фазы 0 — обход стека). Самый широкий язык обычно русский.
- Честность: только реальные данные, никаких обещаний прибыли, прогнозов и «винрейта», везде
  «Не финансовый совет». Правила сигналов (`SignalRules`) без нового исследования не менять.
- Бюджеты размера страниц (`budget.e2e.ts`) молча не поднимать; тяжёлое — отдельным чанком.
- Всё, что требует настроек владельца, выключено по умолчанию и без них ничего не ломает.
- **Новые зависимости — только с обоснованием в PR** (почему своё хуже).

### Регресс-проход в конце каждой фазы

Последний PR фазы содержит таблицу «что прогнано и что вышло»:

1. Все наборы: `backend ./gradlew build`, `web npm test && npx tsc --noEmit && npm run e2e`,
   `video npm test && npx tsc --noEmit`, `research` pytest.
2. Обход стека из 0.1 (десктоп и телефон, все языки) и визуальные снимки из 0.2.
3. Короткая нагрузка на `FakeExchange`: `loadtest/run.sh --local-build visitors -e VUS=100 -e HOLD=1m`.
   Цифры сравнить с прошлым прогоном; просадка больше 20% — разобрать до конца фазы.
4. Найденное и неисправленное — задачей в следующую фазу, с описанием.
5. В `CLAUDE.md` — новое из «выучено на ошибках», если оно было.

## Что недоступно в облаке

- Живой стек и база — на маке владельца: деплой и миграции делает локальная сессия.
- `fapi.binance.com` отвечает 451: для данных — архив `data.binance.vision`, для тестов —
  `pulse.fake-market.enabled` и фикстуры. На подставном рынке пары называются `FAKE000USDT`…: брать
  пару из `/api/summary`, а не `BTCUSDT`.
- Docker в облачном контейнере после перезапуска сессии лежит: `sudo dockerd &`, потом
  `sudo chmod 666 /var/run/docker.sock`. Gradle внутри Docker не проходит прокси: образы стенда —
  `--local-build` (jar и сайт собираются снаружи).
- Аккаунты, токены, ключи, оплата, публикации — только владелец (фаза 8).

## Порядок и параллельность

1. Фаза 0 — до всего остального: она проверяет всё, что будет сделано потом.
2. Фазы 1 → 2 → 3 по порядку: честность, ценность, запас.
3. Фазы 4 и 5 можно вести параллельно с 2–3 другой сессией: `video/` и инфраструктура почти не
   пересекаются с `web/`.
4. Фазы 6 и 7 — дизайн и вопрос владельцу, без реализации.

Общие файлы (`locale-*.ts`, `application.yml`, миграции, `sitemap.xml`, `ci.yml`) — следующим
свободным номером, конфликты решать, сохраняя обе стороны (так решались все конфликты PLAN-4).

**Полная готовность:** фазы 0–5 закрыты PR-ами с зелёным CI и регресс-проходом, обход стека
работает в CI каждый день, сторож 1.1 работает, новая пачка роликов лежит в Release, вопросы фаз 6–7
заданы, а всё, что ждёт владельца, перечислено в последнем PR.

Не финансовый совет.
