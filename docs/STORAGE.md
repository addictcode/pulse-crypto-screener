# Хранение: что растёт, как читается, как восстанавливается

PLAN-5, задача 1.5. Замер 9.11.2026 на стенде (`loadtest/run.sh --local-build up`, PostgreSQL 17,
4 vCPU): в `signal` залит **1 000 000** синтетических сигналов, по одному в 15 секунд (173 дня),
400 пар, 7 типов, с исходами.

## Что растёт

| Таблица | Рост | Что с ним делать |
|---|---|---|
| `signal` | ~480 байт строка с индексами; 1 млн строк = 483 МБ | читается только по индексам (ниже); старые подробности — `deploy/prune.sh` |
| `signal_day` | 14 строк в день (тип × направление) | ничего: ~5 000 строк в год |
| `visit_day` | день × страница × источник — десятки строк в день | ничего |
| `push_subscription` | строка на браузер; уникальный индекс по `endpoint` | мёртвые подписки удаляются при ответе 404/410 push-сервиса |
| `client_error` | одна строка на разную ошибку, живёт сутки | чистится сам (0.3) |
| `signal_audit`, `uptime` | строка в сутки / на запуск | ничего |

Сколько сигналов в день на настоящем рынке, станет видно после деплоя (`select count(*) from signal
where fired_at > now() - interval '1 day'`). При 1 000 в день миллион наберётся за три года.

## Планы запросов на 1 млн строк

| Запрос | Где | План | Время |
|---|---|---|---|
| последние 50 | лента, бот | Index Scan `ix_signal_fired_at` | 0,1 мс |
| последние 50 пары | история пары | Index Scan `ix_signal_symbol_fired_at` | 0,3 мс |
| без исхода за час | `OutcomeTracker` раз в 20 с | Index Scan `ix_signal_fired_at` | 0,1 мс |
| сигналы за сутки | сверка 1.1 раз в сутки | Index Scan `ix_signal_fired_at` (6 000 строк) | 2,7 мс |
| статистика за 7 дней | `/record/`, бот | Index Scan, 40 000 строк | 23 мс |
| **статистика за 90 дней** | `/record/` | Parallel Index Scan, 520 000 строк | **123 мс, на каждый заход** |
| все `fired_at` | `UptimeLog`, один раз при первом запуске | Index Only Scan | 433 мс |

Узкое место одно — статистика `/record/`: при наплыве каждый зритель стоил бы базе 123 мс. Теперь:

- **`signal_day`** (миграция 017, `SignalRollup`): суммы исходов по дням, типам и направлениям. День
  сворачивается в 01:31 UTC следующего дня и ещё раз через сутки (на случай позднего исхода);
  первый запуск сворачивает все прошлые дни (173 дня — за пару секунд). Статистика берёт целые
  дни из `signal_day` (1 232 строки, Bitmap Index Scan, **1 мс**), а края периода — из `signal`.
  Если хоть один день периода не свёрнут — честно считает по сигналам, как раньше. Тест
  `SignalRollupIT` сверяет оба пути до 1e-9.
- **Кэш на минуту** по длине периода (`SignalHistory.outcomes`): 90 дней по HTTP — 18 мс без кэша,
  6 мс из кэша (было ~125 мс на каждый заход).

## Срок хранения подробностей

`deploy/prune.sh` сначала делает дамп (`deploy/backup.sh pre-prune`, без него не идёт дальше), потом
очищает текст `detail` у сигналов старше `PULSE_DETAIL_DAYS` (180 дней). Тип, пара, время, цена,
значение, направление и исходы остаются навсегда — это статистика и исследования. Запускает
владелец руками, когда таблица станет заметной. Замер: на 827 тыс. строк — 20 секунд. Файл таблицы
после этого не уменьшается (PostgreSQL переиспользует место под новые строки); вернуть место
системе может только `VACUUM FULL signal`, а он запирает таблицу — делать в тихий час и с дампом.

## Бэкап, который проверяли

- `deploy/backup.sh` рядом с каждым дампом пишет `*.dump.counts`: строки каждой таблицы прямо перед
  дампом.
- `deploy/restore-check.sh [дамп]` поднимает новейший дамп в одноразовом контейнере `postgres:17-alpine`
  и сверяет строки каждой таблицы: в восстановленном не меньше, чем было перед дампом. Иначе —
  код 1 и «RESTORE CHECK FAILED». Дамп с 1 млн сигналов (44 МБ) восстанавливается и сверяется за 15 с.
- На сервере — раз в неделю (воскресенье 04:20, cron из `deploy/oracle/setup.sh`, лог
  `/home/pulse/restore-check.log`); на маке — `deploy/home.sh check`.
